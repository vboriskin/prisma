# Аудит таблицы сотрудников: User-jobs и owner-job clarity

**Эксперт:** Product Manager в B2B-tools (jobs-to-be-done lens; mantra: «если не можешь назвать решение тимлида, которое фича поддерживает — выпили»)
**Дата:** 2026-06-02

## Резюме

Roster выглядит как мощная диагностика, но при попытке назвать конкретное **решение тимлида** для каждой колонки получается неприятный список: ~40% контента в строке и ~60% контента в detail panel **не привязаны ни к какому owner-job**. Это дашборд-карго-культ — много сигнала, low decision-density.

Главный конфликт: фича позиционируется как «утренние 5 минут перед stand-up», но reality — это **inspection-tool на 25 минут**, где тимлид должен сам собрать решение из 13 чипов, heatmap'а 360 клеток, narrative-листа и 3 кнопок копирования. Owner-job «принимаю решение кому помочь сегодня» закрыт **косвенно** через классификацию stop/watch/moving/idle, но дальше — bloat.

Конкретно: persona метрики (PROD/SWITCH/LOC/FRT/burnout) живут за productivity-флагом — это сразу сигнал, что у них **нет owner-job у тимлида**. CRV/PRT chips дублируют решение «merge or not» которое к тимлиду не относится. CR-chip в строке не подсказывает «что делать», а только говорит «у этого ревьюера медиана 6ч» — actionability близка к 0.

Ниже 12 находок, каждая с явным User-job и Сейчас vs Должно быть.

## Находки

### 1. Roster — это inspection-mode, а не decision-mode

**User-job (overt):** «Утром перед stand-up за 5 минут понять, к кому подойти первым и про что».

**Описание:** Roster плотно нагружен данными (24×2 dot-strips + 4 счётчика + до 6 бэйджей + 4 source-chips на строку), но **финальное решение «к кому подойти»** не выделено визуально. Group head «Требует внимания» с number — это категория, но **внутри stop-группы** строки сортируются по `timelineToday desc, timelineYesterday desc` (см. `teamScanner2RendererPersonRows.js:71-76`) — то есть по объёму активности, а не по приоритету разговора. Тимлид должен «прочитать» строку, чтобы понять разницу между двумя людьми в stop.

В `teamScanner2Insights.js:147-195` уже есть `buildActionQueue(model)` — pure-rule приоритизация с severity score и готовым `action: '1:1 разговор — что мешает'`. Эта очередь **не отображается в roster** (используется только в Insights/брифе). Это явный продуктовый разрыв: лучший компонент для owner-job спрятан, а его место занимает таблица.

**Зачем чинить:** Текущий roster закрывает inspection-job («что у команды происходит»). Owner-job в реальном workflow тимлида — **«с кем поговорить сегодня и про что»**. Без явного top-N actions roster требует когнитивной нагрузки, которую как раз обещали снять.

**Как чинить:**
- Над roster — карточка «Сегодня поговори с» (top-3 из `buildActionQueue` с reason + action + кнопкой «Скопировать talking-points»).
- Roster ниже остаётся как drill-down inspection-mode.
- Pseudo-code:
```js
const topActions = buildActionQueue(model).slice(0, 3);
return `
  ${renderTopActionsBlock(topActions)}  // новый primary block
  ${renderPersonRows(model, ctx)}        // demoted to "вся команда"
`;
```

**Критичность:** high. **Сложность:** medium. **Ценность:** high.

**Сейчас vs Должно быть:**
- Сейчас: Тимлид сканирует «Требует внимания: 5» → читает 5 строк → принимает решение.
- Должно быть: Тимлид видит «Сегодня: Иванов (96ч stop), Петров (overload 4 WIP), Сидорова (burnout high)» → 3 кнопки «Talking-points» → готов к stand-up за 60 секунд.

### 2. PROD/SWITCH/LOC chips за productivity-флагом — это feature-zombie

**User-job:** (не существует у тимлида)

**Описание:** В `teamScanner2Renderer.js:1257-1306` chips PROD/SWITCH/LOC скрыты за `localStorage.q2_scanner_show_productivity = '1'`. Это **антипаттерн**: если фича доступна только через ручной flag, она либо (а) не нужна никому, либо (б) нужна нишевой роли (engineering manager в другом контексте). В обоих случаях — feature-zombie.

Комментарий честно говорит: «По Birman: для PM productivity-score не интерпретируется без обучения» (line 1258). Это buy-in от автора: метрика существует, но решение тимлида от неё не зависит.

`composite burnout-сигнал` (line 1330) — единственное из этой группы, где есть actionable hook («стоп → разговор»), но в данный момент он скрыт тем же флагом видимости что и токсичные метрики.

**Зачем чинить:** Снять technical debt и cognitive overhead на чтение кода. Если кто-то всё-таки откроет flag — увидит decoupled от решений набор цифр, которые невозможно интерпретировать в действие.

**Как чинить:**
- PROD: удалить полностью. Score = сумма произведений × 5 эвристик. Если нужен composite — должен быть в Аналитике/AI-Анализе, не в Сканнере.
- SWITCH: удалить ↻N badge из row тоже (line 242-244). Действие тимлида от switch-rate не зависит.
- LOC: удалить. LOC ≈ commits × 50 — приближение к плохой метрике.
- BURNOUT: вытащить из-за флага, оставить **только высокий level** в roster как row badge (по аналогии с dwell-badge). Никаких composite score'ов — просто `▌Burnout high` с tooltip «Признаки: weekend×N · late-night × M». Это actionable: «уточни на 1:1 про загрузку».
- FRT: переоценить. Сейчас формула описывает «медиана dwell в open/todo» — это proxy на review-time, но как тимлид решает что-то на основе этой цифры? Если ответ «никак» — удалить.

**Критичность:** medium. **Сложность:** low. **Ценность:** high (cleanup).

**Сейчас vs Должно быть:**
- Сейчас: 5 chips за флагом, которые «нельзя интерпретировать без обучения». Любой, кто включит flag в браузере, увидит мусор.
- Должно быть: 0-1 chip (burnout high) с явной next-action. Productivity-метрики вырезаны, их место — в специализированной аналитике для engineering managers, не в operational scanner'е.

### 3. CR Nч и N↗ Z% chips в строке без owner-job

**User-job (overt):** «Понять, кто из команды узкое место в code review».

**Описание:** В `teamScanner2RendererPersonRows.js:248-256` rendering CRV ('CR 6ч') и PR throughput ('N↗ 80%') chips. Это chips бэйджи **per-row**, видны в утреннем roster'е. Вопрос: какое решение тимлида они поддерживают?

Сценарии:
1. «Перевести review другому ревьюеру» — нет ручки в roster, тимлид должен идти в Jira/BB.
2. «Поговорить с этим ревьюером, чтобы быстрее ревьюил» — но это action на 1:1, не в roster.
3. «Понять system-level узкое место в CR» — это team-level KPI, не per-person.

Сам chip CR Nч **не показывает дельту от прошлого**, не подсвечивает ухудшение, не сравнивает с командой. Это просто число. Тимлид может посмотреть и… что? Если число большое — что ему делать прямо сейчас?

PRT chip `N↗ 80%` — показывает opened/merged ratio. Решение тимлида: «помочь приоритизировать PR-ы», но эта подсказка появляется только если `flag === 'overload'` через спавнинг кнопки в panel header (line 1435-1438) — то есть **не в roster**.

**Зачем чинить:** В B2B-tools плохо, когда метрика показывается, но к ней нет «и что дальше». Это создаёт нагрузку «надо ли мне реагировать» без подсказки.

**Как чинить:**
- В строке оставить **только** PR throughput при `flag === 'overload'` (signal-as-badge: «PR overload»).
- CRV убрать из строки. Поднять как team-level KPI в шапку (например, «P50 CR-time команды: 6ч, при норме 4ч» — это решение масштаба команды, не персоны).
- В detail panel оставить CR chip + сравнение с командной медианой, но **только если ревьюер реально может что-то поменять** — например, «За 14д: 8 ревью, медиана 12ч (×2 от команды). Возможные причины: перегружен другими PR / большой PR / нет контекста».

**Критичность:** medium. **Сложность:** low. **Ценность:** medium.

**Сейчас vs Должно быть:**
- Сейчас: 2 chip'а в строке без actionability; тимлид видит цифры, но не знает, что с ними делать.
- Должно быть: 1 signal-as-badge только при overload + team-level CRV-KPI в шапке + развёрнутый chip в detail panel с интерпретацией.

### 4. Heatmap 72×4 — внушительный артефакт без явного решения

**User-job (claimed):** «Понять паттерны работы сотрудника по источникам».

**Описание:** 360 клеток (72 × 5 источников) с opacity-scale. Это level-3 диагностика (комментарий в коде, line 201). Реальные решения тимлида от heatmap'а: «понять, что человек работает ночью» (burnout proxy), «понять, где пик активности» (capacity planning).

Но: оба этих job'а лучше закрываются **специализированными виджетами**:
- Late-night activity → отдельный flag/badge (например, ▌Night-work если ≥25% событий после 22:00).
- Peak hours → одна строка «Пик: вчера 14-16ч в Jira» вместо grid'а.

В текущем виде heatmap занимает большую часть detail panel, перегружает PIN-картирование и требует тимлида расшифровывать сетку, чтобы найти «что-то одно». Это inversion of user goal.

В жалобах экспертов на предыдущих аудитах прямо отмечено: «heatmap занимает много места».

**Зачем чинить:** Detail panel должна стать **focus view** — что-то одно главное. Heatmap превращает её в дашборд.

**Как чинить:**
- Свернуть heatmap в `<details>` (как уже сделано с blockers shelf и assistant section).
- Оставить **только** компактный summary под counters: «Пик: вчера 14-16ч в Jira · 80% работы в часы 10-18».
- Открывать grid по click — drill-down.

**Критичность:** medium. **Сложность:** low. **Ценность:** medium.

**Сейчас vs Должно быть:**
- Сейчас: heatmap занимает ~30% высоты panel, открыт по умолчанию, никак не помогает тимлиду принять решение за 5 минут.
- Должно быть: ОДИН summary line («Пик: 14-16ч Jira») + collapsible grid для тех, кто хочет глубже.

### 5. EventsFeed дублирует heatmap, но открыт по умолчанию

**User-job (overt):** «Прочитать что человек делал за 72 часа».

**Описание:** `renderEventsFeed` в `teamScanner2Renderer.js:1691+` рендерит timeline 72ч сгруппированный по bucket'ам today/yesterday/dayBefore/older. Комментарий line 1739-1742 честно говорит: «event-log дублирует данные heatmap72×4 (те же 22 события на 5 источниках × 72 часах). Не удаляем (drill-down value), но сворачиваем в `<details>` — heatmap остаётся primary view».

Это **правильный продуктовый instinct**, но конфликт: в `renderEmployeeDetailPanel` (line 1152) `renderEventsFeed` рендерится как обычная секция, не под `<details>` — хотя комментарий обещает обратное. Либо комментарий устарел, либо сворачивание реализовано не до конца. Проверка: line 1742 говорит «свёрнуто», но сама функция не оборачивает в `<details>` на line 1733+.

Решение тимлида от events feed: «найти конкретный коммент/PR/transition» — это **inspection job**, не decision job. Это «когда стало плохо», не «что делать сегодня».

**Зачем чинить:** Detail panel должна закрывать main job (decision: подойти / не подойти / про что говорить) первыми 30 секундами. Events feed как primary section ломает приоритизацию.

**Как чинить:**
- Применить уже задеклеренный intent — обернуть events feed в `<details>` collapsed by default.
- Pseudo-code:
```js
// в renderEventsFeed заменить outer wrapper:
return `
  <details class="ts2-panel-section ts2-events-details">
    <summary class="ts2-panel-section-title">События за 72ч ${esc(total)}</summary>
    ${body}
  </details>
`;
```

**Критичность:** medium. **Сложность:** low. **Ценность:** medium.

**Сейчас vs Должно быть:**
- Сейчас: events feed открыт, дублирует heatmap, занимает место.
- Должно быть: collapsed, открывается по click для drill-down.

### 6. «Копировать для 1:1» — три почти одинаковые кнопки

**User-job (overt):** «Скопировать summary человека в TG/Slack для async-команды».

**Описание:** В detail panel header есть три кнопки, делающие почти одно и то же:
1. `#ts2-detail-tgcopy` ('TG') — копирует 5-7 строк plain-text (line 2752-2799).
2. `#ts2-detail-share` (link icon) — копирует permalink (line 2801+).
3. `.ts2-narrative-copy` ('Копировать') — копирует markdown narrative (line 2365+).
4. `#ts2-detail-spawn-1on1` ('Обсудить 1:1') — копирует talking-points для PR overload (line 2724+).

Каждая выбрасывает разный output, разная аудитория, разные триггеры. Тимлид не знает заранее, что какая кнопка делает. UI выглядит как «выбор из четырёх», но каждая использует разный context (5 строк, markdown, link, talking-points).

**Зачем чинить:** Это violates «единый actionable export». Тимлид должен **один раз** скопировать summary под нужный контекст — а сейчас у него **четыре** способа сделать почти то же самое.

**Как чинить:**
- Объединить в одну primary action: **«Скопировать сводку»** с **dropdown пресетов**:
  - «Для Telegram (5 строк)»
  - «Для 1:1 (markdown + talking-points)»
  - «Permalink (ссылка на этот вид)»
- Это снимает «какая кнопка нужна?» загадку и оставляет одну primary action в header.

**Критичность:** medium. **Сложность:** medium. **Ценность:** medium.

**Сейчас vs Должно быть:**
- Сейчас: 4 кнопки в header с tooltip'ами, надо помнить какая что делает.
- Должно быть: 1 кнопка + 3 пресета (либо dropdown, либо primary + secondary).

### 7. Source-chips B/J/C/Zc/Ze в строке: read-only, не actionable

**User-job (claimed):** «Видеть multi-source signal на уровне строки».

**Описание:** `srcChips` в `teamScanner2RendererPersonRows.js:228-230` рендерят чипы «B 2», «J 3», «C 0» и т.д. Это **информационные** chips, **не кликабельные**, **не filter'ы**. Решение тимлида: «понимать что человек работает в нескольких источниках».

Но: эта инфо уже есть в **dot-strips сегодня/вчера** (визуально показывают, сколько событий есть). И есть в **counters**: «3 задач · 8 часов». Source-chips дают разрез по типу источника, но не привязаны к решению.

Если их функция — **«доверять данным или нет»** (например, J⚠ = jenkins недоступен, line 226), то это **отдельный сигнал «integration health»**, который должен жить **на уровне команды** или баннера, не на каждой строке.

**Зачем чинить:** Каждый чип в строке должен закрывать одно из:
- (а) показывать risk/action (как dwell-badge ▌48ч → «discuss today»);
- (б) быть filter'ом («показать только тех, у кого есть BB-активность»);
- (в) быть deep-link («открыть BB-список этого человека за 72ч»).

Сейчас они не делают ничего из этого.

**Как чинить:**
- J⚠ (jenkins error): вытащить **на уровень группы** или баннер в шапке («Jenkins недоступен — N сотрудников без данных»). Не дублировать на каждую строку.
- B/C/Zc/Ze chips: сделать **кликабельными** — клик ведёт в detail panel с **префильтром** (Zc → открыть panel с активным filter zc). Это привязывает к job «понять, что человек делал в этом источнике».
- Альтернатива: удалить из строки, оставить только в detail panel.

**Критичность:** low. **Сложность:** low. **Ценность:** medium.

**Сейчас vs Должно быть:**
- Сейчас: 4 read-only chip'а, дублирующие информацию из dot-strips и counters.
- Должно быть: либо deep-link в panel с filter, либо удалить вовсе.

### 8. Sprint context отсутствует в roster — каждый человек оторван от спринта

**User-job (overt):** «Понять, кто из команды стоит на критичном пути спринта».

**Описание:** Roster показывает «3 задач затронуто за 72ч» как counter, но **никак не сигнализирует**, какие из этих задач — sprint-critical (с приближающимся due date / sprint goal-задачи / на критичном пути зависимостей).

`composePersonNarrative` (Insights, line 1000+) использует `p.issuesNow` и `p.timelineToday`, но не передаёт sprint-criticality в строку. Если Иванов трогает 5 задач, но **ни одной из спринта** — это сигнал «работает не туда» и должен подняться. Сейчас не поднимается.

Аналогично: если у двух сотрудников одинаково «stop · 2 блокера», но у одного блокер — sprint-critical, а у другого — backlog — приоритет разговора **совершенно разный**, но roster не отличает.

**Зачем чинить:** Owner-job тимлида — **спринт-делает или не делает**. Roster закрывает «активность есть или нет», но не связывает с целью.

**Как чинить:**
- Подкрасить (или добавить chip) к строке, если **WIP-задачи не из активного спринта** — например, ⚠ «вне спринта» chip.
- В блокерах подсветить sprint-critical жирным или красным border.
- В counters: «3 задач · из них 1 в спринте» — простое дополнение.
- Pseudo-code:
```js
const wipInSprint = (p.issuesNow || []).filter(it => isInActiveSprint(it, model.scannerV2?.sprintGoal));
const wipOutSprint = wipN - wipInSprint.length;
const wipBadge = wipOutSprint > 0
  ? `<span class="ts2-row-out-sprint" title="${wipOutSprint} из ${wipN} вне активного спринта">⚠ ${wipOutSprint} вне спринта</span>`
  : '';
```

**Критичность:** high. **Сложность:** medium. **Ценность:** high.

**Сейчас vs Должно быть:**
- Сейчас: «3 задач затронуто» — все задачи равны. Тимлид не различает sprint vs vne-sprint.
- Должно быть: 2/3 задач в спринте + chip «1 вне» — мгновенно видно «куда уходит время».

### 9. Roster не разделяет «нужен разговор сегодня» от «нужно наблюдать на горизонте недели»

**User-job (overt):** «Понять, что срочно сегодня vs что просто watch».

**Описание:** Группа `watch` собирает **разнородные** случаи через OR в classifier (`teamScanner2Classifier.js:91-93`):
- `wip >= 3` → overload-сигнал (актуально на 1 неделю).
- `stuck > 0 && today > 0` → разговор сегодня (актуально утром).
- `today === 0 && yest > 0` → vacuum-сигнал (актуально немедленно «жив ли?»).

Это три разных решения тимлида, агрегированные в одну группу. Тимлид видит «5 в watch» и должен сам читать каждую строку, чтобы понять, что именно происходит.

В `buildActionQueue` (line 169-180) уже есть **различение** через severity (70 для overload, 60 для watch+dwell, 40 для burnout-medium), но это **не отражается** в группировке roster.

**Зачем чинить:** Watch-группа становится «всё остальное непонятное» — отсутствие приоритизации внутри.

**Как чинить:**
- Внутри watch отсортировать **по типу сигнала**, не по timeline:
  1. Первым — те, у кого `stuck > 0 && today > 0` (нужен разговор сегодня).
  2. Затем `wip >= 3` (overload).
  3. Затем `today === 0 && yest > 0` (vacuum).
- Внутри **подсветить** в строке тип сигнала: «overload», «застрял-но-работает», «тихо после активного».
- Pseudo-code: ввести **подгруппы** через `<h3>` mini-headers внутри watch.

**Критичность:** medium. **Сложность:** low. **Ценность:** medium.

**Сейчас vs Должно быть:**
- Сейчас: 5 в watch, тимлид читает каждого, чтобы понять «срочно или не очень».
- Должно быть: подгруппа «требует разговора сегодня (3)» / «overload (2)» / «vacuum (0)» — мгновенно ясно, что срочное.

### 10. Idle-группа всё ещё показывает 4 источника (BB/CF/Z/J) — confusion для тимлида

**User-job (overt):** «Понять, что человек действительно в отпуске vs у нас плохая identity-mapping».

**Описание:** Idle-группа сворачивается в `<details>` (line 137-141), что правильно. Но **внутри строки** idle-сотрудника всё ещё рендерятся **source-chips** (если есть данные) и **counters** (`в пути 0 · PR 0 · 0 задач · 0ч`). 4 нуля — это **noise**, который не отвечает на вопрос «почему idle?».

`composePersonNarrative` (Insights line 982-996) уже **различает два случая**:
- Нет identity-mapping → «настрой в реестре».
- Есть identity, но тишина → «возможно отпуск».

Эта **подсказка существует**, но **только в detail panel**, не в строке roster'а. Тимлид должен раскрыть idle, кликнуть на человека, прочитать narrative, чтобы понять, что делать.

**Зачем чинить:** Idle — это группа **где решение однозначно**: либо «настрой identity», либо «забудь, отпуск». Это самый простой actionable signal — должен быть видим без drill-down.

**Как чинить:**
- В строке idle-сотрудника **заменить** counters на **гипотезу**: либо «настрой identity (нет email/jiraAccountId)», либо «вне рабочих часов / возможно отпуск».
- Pseudo-code:
```js
if (currentGroup === 'idle') {
  const hasIdentity = !!(p.email || p.jiraAccountId || p.bitbucketLogin);
  return hasIdentity
    ? renderIdleRow(p, 'тихо — возможно отпуск')
    : renderIdleRow(p, 'нет identity-mapping — настрой в реестре');
}
```

**Критичность:** medium. **Сложность:** low. **Ценность:** high.

**Сейчас vs Должно быть:**
- Сейчас: 4 нуля + chevron, тимлид кликает чтобы понять.
- Должно быть: одна строка-гипотеза, не нужно кликать.

### 11. «Сегодня / Вчера» dot-strips: high cognitive cost vs low decision yield

**User-job (claimed):** «Понять паттерн активности — равномерно vs всплеск».

**Описание:** В `renderRow` рендерятся два горизонтальных dot-strip'а по 24 точки каждый — сегодня и вчера (line 177-183). Это **визуально** красиво, но какое решение тимлида они поддерживают?

Сценарии:
1. «Видеть, что коммитов сегодня ещё нет» — но **counter** «0 PR · 0ч» это уже говорит.
2. «Видеть, что человек работал ночью» — но dot-strip не различает, был ли это late-night vs early-morning (нет визуальной шкалы часов).
3. «Сравнить плотность активности» — но 24 dot'а на 200px дают разрешение ~8px на дот; точность сравнения низкая.

В жалобах экспертов прошлых аудитов отмечалось «коммиты есть, PR не открывает» как сигнал — но **это не считывается** из dot-strips, потому что точки не цветные по source (один тип точки на весь день).

**Зачем чинить:** Dot-strips занимают ~30% ширины row. Если они не закрывают decision-job, это валюта visual real estate без отдачи.

**Как чинить:**
- Объединить в **один tinted bar** «активность 48ч» (heatmap-стиль, но компактный, 12-16 segment'ов по 4ч).
- Альтернатива: показать **только сегодня** + чип «вчера: M событий» (если число не критично — экономия места).
- Альтернатива #2: dot-strip with colors-by-source — но это нагружает row ещё сильнее.

**Критичность:** low. **Сложность:** medium. **Ценность:** low (косметика, но reduces noise).

**Сейчас vs Должно быть:**
- Сейчас: 2 × 24 dot-strip'а ≈ 300px row width, низкая discriminating power.
- Должно быть: 1 × 12-сегментный mini-heatmap или 1 × 24h + цифра «вчера: 12».

### 12. Narrative в panel: правильный instinct, но не closes-the-loop

**User-job (overt):** «За 30 секунд получить ответ — что делать с этим человеком».

**Описание:** `composePersonNarrative` (Insights line 955-1056) — это **лучшая часть** detail panel: 3-5 предложений на русском, focus на задачах, hypothesis для empty-state. Это closest-to-user-job компонент во всей фиче.

Но: narrative **не предлагает next action**. Тимлид читает «Сегодня: трогал CORE-13, CORE-21. Блокер: CORE-9 нет движения 48ч (статус "Code Review"). Вчера: 8 событий по CORE-13.», и… что? Это **observation**, не **recommendation**.

В `buildActionQueue` (line 147-195) уже есть **action-rules**: «1:1 разговор — что мешает» / «Помоги приоритизировать» / «Спроси на stand-up». Эти actions **не появляются в narrative** detail panel'и.

**Зачем чинить:** Narrative — это правильный формат для тимлида (текст, не таблица), но без action она остаётся «обзорной справкой». Closing-the-loop требует «и что делать».

**Как чинить:**
- В конец narrative добавить **recommended action** из `buildActionQueue`:
  ```
  Сегодня: трогал CORE-13, CORE-21.
  Блокер: CORE-9 нет движения 48ч (статус "Code Review").
  Вчера: 8 событий по CORE-13.

  → Рекомендуемое действие: 1:1 разговор — что мешает CORE-9.
  ```
- Кнопка «Скопировать» уже копирует narrative — расширить, чтобы включала action.
- Опционально: кнопка «Создать reminder» / «Запланировать 1:1» (deep-link в TG/Slack/Outlook).

**Критичность:** high. **Сложность:** low. **Ценность:** high.

**Сейчас vs Должно быть:**
- Сейчас: narrative описывает «что случилось», тимлид сам додумывает «что делать».
- Должно быть: narrative заканчивается рекомендацией + кнопкой одной из 3 actions (1:1 / stand-up / wait-watch).

### 13. LLM-сводка ассистента — отдельная коробка, не интегрирована с narrative

**User-job (claimed):** «Получить умную интерпретацию данных».

**Описание:** В `teamScanner2Renderer.js:1170-1190` — `renderAssistantSection` со «Сводка за 72ч» и «План сегодня / факт вчера». Это `<details>` collapsed by default, lazy-load LLM (GigaChat).

Концептуально хорошо: LLM может дать то, что rule-based composePersonNarrative не может. Но в текущем UI **две сводки живут рядом** — rule-based narrative сверху, LLM-summary в `<details>` ниже. Это **two parallel attempts at the same job**.

Тимлид видит сначала rule-based summary (моментально, бесплатно), потом видит «Сводка ассистента — генерируется GigaChat», кликает, ждёт 5-10 секунд, читает LLM-вариант, **сравнивает** с rule-based. Это inverted user-flow: «лучшее» (LLM) почему-то спрятано, «среднее» (rule-based) — primary.

**Зачем чинить:** Либо LLM-сводка **заменяет** narrative (тогда rule-based — fallback при сбое LLM), либо они **закрывают разные jobs** (тогда нужно разделить — например, narrative=overview, LLM=hypothesis-of-cause).

**Как чинить:**
- Вариант A (radical): rule-based composePersonNarrative — это fallback при ошибке LLM. По умолчанию открывается LLM-сводка с placeholder «генерация…», параллельно показывается rule-based (если LLM не успела).
- Вариант B (incremental): четко **разделить jobs**:
  - narrative = «что произошло» (rule-based, instant).
  - LLM = «почему / гипотеза» (план/факт).
  Не дублировать «summary за 72ч» в обоих местах. Изменить заголовок LLM-блока: «Гипотеза о плане сегодня / разрыв с фактом вчера».

**Критичность:** medium. **Сложность:** medium. **Ценность:** medium.

**Сейчас vs Должно быть:**
- Сейчас: 2 параллельные сводки, тимлид не знает, какая «правильная».
- Должно быть: 1 primary narrative + LLM hypothesis о причине (или LLM как primary с rule-based fallback).
