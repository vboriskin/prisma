# Аудит вкладки «КУРС · ИНСАЙТЫ»

Дата: 2026-05-05 · Версия: V21 (tabs-consolidation) · Эксперты: IA, UX, Visual/Brand, FE/Perf

## Контекст и факты

- Пункт меню «Инсайты» (sidebar модуль **КУРС**, `index.html:618-621`) → секция `#section-insights` (`index.html:1132-1136`).
- Рендерит `InsightsView` из `views/metrics.js:481-581` (НЕ из `views/insightsDashboards.js` — это путаница, см. п.6).
- Содержимое: `renderHero` (kpi = high+medium count) + 3 списка (Критические / Внимания / Операционные) + 2 списка (Команды по риску, Ключевые проблемы данных). Около 25 KPI-сигналов, 100 % считаются прямо из `FilterEngine.getFiltered()` — НЕ зависит от Сканнера 2.0 / Pulse / BB.
- 4 V21-дашборда (`EstimationCalibrationView`, `ComponentHealthView`, `BurnoutWatchtowerView`, `DocDebtConsoleView`) — в `views/insightsDashboards.js`, **в другом модуле** sidebar (СОСТОЯНИЕ), на отдельных пунктах меню. Они не относятся к этой вкладке, несмотря на похожее имя файла.
- Легенда «Инсайты»: 3 цвета high/medium/low (`app.js:1704-1708`).
- Брендбук цвет «Инсайт» = `#B084CC / #6B4488` (`BRAND_BOOK.md:113`) — в текущем рендере НЕ используется ни разу. Используются стандартные high=red / medium=yellow / low=green (`styles.css:3175-3177`).
- На дашборде уже есть очень похожий блок («Сводка метрик» / hero). На «Метрики» — был дубликат «Операционные сигналы», удалён в П4-MS Wave 5 (`views/metrics.js:230-235`) — комментарий явно говорит: «Полный обзор сигналов теперь только в `section-insights`».

## 1. [HIGH · IA] Вкладка живёт «не в той семье»

**Что найдено:** «Инсайты» в sidebar — пункт модуля **КУРС** (рядом с Дашбордом и Метриками). Но соседние тимлид-инструменты («Перегрузка», «Здоровье компонентов», «Точность оценок», «Документация», `index.html:689-754`) распределены по двум другим модулям (СОСТОЯНИЕ / ИНТЕГРАЦИИ). По смыслу все 5 вкладок — это «инсайты разной природы», но IA их разорвал.

**Где:** `index.html:618-621` (КУРС/Инсайты) vs `index.html:687-694` (СОСТОЯНИЕ/Перегрузка-ЗдКомп) vs `index.html:746-755` (ИНТЕГР/Точность-Документация).

**По-человечески:** пользователь видит «Инсайты» в КУРС, ждёт что там — все сигналы. Открывает — видит 6 строк по filtered registry. Чтобы найти burnout / hot files / doc-debt — должен вспомнить про другие три модуля sidebar. Mental model сломан.

**Предложение:** либо (а) переименовать «Инсайты» → «Сигналы курса» и явно ограничить scope = «только данные Реестра», либо (б) собрать все 5 в один модуль СИГНАЛЫ (см. раздел «Рекомендация по консолидации»).

## 2. [HIGH · UX/Product] Информационная плотность ниже плинтуса

**Что найдено:** на всю вкладку — ~25 счётчиков (`views/metrics.js:495-517`). Hero KPI = «N сигналов за неделю» (хотя считается из текущего snapshot, а не за неделю — формулировка вводит в заблуждение, `views/metrics.js:557-560`). Каждый сигнал — одна цифра без drill-down: ткнуть на «Блокеры в ближайших релизах = 3» — ничего не происходит, нельзя посмотреть какие именно.

**Где:** `views/metrics.js:495-517`, `views/metrics.js:557` (`'СИГНАЛОВ ЗА НЕДЕЛЮ'` — фраза неверная), `views/metrics.js:530-538` (`renderList` — без onclick на items).

**По-человечески:** вкладка делает одну работу — «показать число» — за вычетом 3 action-кнопок («Назначить в 1.20», «Перевести в Да», «Снять блокеры», `views/metrics.js:543-551`). Пользователь не может провалиться в список задач. Это анти-паттерн «metrics dead-end».

**Предложение:** каждый счётчик → кликабелен → открывает Реестр с pre-applied фильтром (router-deeplink `#registry?filter=blockers120`). Hero caption поменять на «АКТИВНЫХ СИГНАЛОВ» (без «за неделю», т. к. не ограничено по времени) или ввести реальное window-фильтр.

## 3. [HIGH · UX] Дублирование с Дашбордом

**Что найдено:** Дашборд уже имеет hero с сигналами (`renderHero`), `MetricsView` тоже (`views/metrics.js:248-259`). На «Инсайтах» снова hero + 3 колонки + 2 колонки. Из 25 показателей 4 точно совпадают с уже-удалёнными `opsSignals` в Метриках (комментарий `views/metrics.js:231` подтверждает: «4 точные дубли high/medium»).

**Где:** `views/metrics.js:559-579` (Insights wrap), `views/metrics.js:248-259` (Metrics hero), `views/dashboard.js` (hero).

**По-человечески:** пользователь видит одни и те же цифры в трёх местах. Doch-fix П4-MS Wave 5 уже частично сделал (вытащил opsSignals из метрик), но недодел: Дашборд + Инсайты теперь делят роль «обзорного экрана».

**Предложение:** Дашборд = «как сейчас идут дела» (% выполнения, KPI), Инсайты должны быть «что требует моего внимания прямо сейчас» (только actionable + сортировка по severity). Удалить из Insights блок «Ключевые проблемы данных» (qualité-данных) — это содержательно `Диагностика` (`views/metrics.js:572-577`).

## 4. [MEDIUM · Visual/Brand] Брендовый цвет «Инсайт» не используется

**Что найдено:** брендбук определяет фирменный цвет «Инсайт» = лаванда `#B084CC / #6B4488` (`BRAND_BOOK.md:113`). На вкладке Инсайтов — ни одной такой штриха. Используется generic high=`#fee2e2/#b91c1c`, medium=`#fef3c7`, low=`#dcfce7` (`styles.css:3175-3177`).

**Где:** `styles.css:3160-3177`, `app.js:1704-1708` (легенда тоже использует не-брендовые `#dc2626/#f59e0b/#22c55e`).

**По-человечески:** название модуля = «Инсайт», у него есть собственный фирменный цвет, но визуально страница выглядит как обычный warning-dashboard. Брендинг не считывается.

**Предложение:** hero-block (рамка 3 px stripe-left, см. `docs/spine-pill.md`) — лавандовый `#B084CC`. Иконка пункта sidebar (`index.html:619`, лампочка) — тоже tint лавандой. Severity-badges оставить как есть (semantic colors), но general accent — лаванда.

## 5. [MEDIUM · Visual/Brand] Hero KPI хардкод-формулировка нарушает «Mono-tabular numerals»

**Что найдено:** caption «СИГНАЛОВ ЗА НЕДЕЛЮ» — ВЕРХНИЙ РЕГИСТР согласно гайду (CLAUDE.md § Принципы), но число `totalSignals` рендерится через generic `renderHero` без явного `font-feature-settings: "tnum"`. Также формулировка ложная (см. п. 2).

**Где:** `views/metrics.js:557-560`.

**По-человечески:** при цифре 12 → 9 строка hero «дрожит» (proportional figures, шрифт SF Pro Display без tnum). Брендбук требует tabular numerals на дашбордах.

**Предложение:** проверить что `renderHero` применяет `class="tnum"` либо CSS `font-variant-numeric: tabular-nums`; добавить в `.summary-hero-kpi` если нет.

## 6. [MEDIUM · FE/Naming] Файл `views/insightsDashboards.js` НЕ относится к вкладке «Инсайты»

**Что найдено:** файл `views/insightsDashboards.js` (357 LOC) рендерит 4 ОТДЕЛЬНЫЕ секции (`#section-est-calibration`, `#section-component-health`, `#section-burnout`, `#section-doc-debt`), а не `#section-insights`. Имя ужасно вводит в заблуждение, особенно когда file header гласит «INSIGHTS DASHBOARDS — V21 AO/AP» (`views/insightsDashboards.js:2-13`).

**Где:** `views/insightsDashboards.js:1-14` vs реальный `InsightsView` в `views/metrics.js:481`.

**По-человечески:** новый разработчик/агент ищет «Инсайты» → находит `insightsDashboards.js` → правит → не видит изменений на вкладке Инсайты, потому что эта вкладка живёт в `metrics.js`. Уже сегодня попытка дать тебе исходник по «Insights» вначале промахнулась мимо.

**Предложение:** переименовать `views/insightsDashboards.js` → `views/teamHealthDashboards.js` ИЛИ `views/v21Dashboards.js`. ДОПОЛНИТЕЛЬНО: вынести `InsightsView` из `metrics.js` в отдельный `views/insightsView.js` (логически они разные домены, sat в одном файле исторически).

## 7. [MEDIUM · UX] Action-кнопки без подтверждения и без видимых результатов

**Что найдено:** 3 кнопки (`assign_120`, `confirm_scope`, `clear_blockers`) рендерятся через `data-action`. Они меняют состояние массово. В коде вкладки нет ни диалога подтверждения, ни тоста об успехе/числе изменённых записей.

**Где:** `views/metrics.js:528, 543-551`.

**По-человечески:** «Снять блокеры →» — массово очищает поля. Если случайно нажал — ничего не откатишь без History (если она ещё доступна). Для тимлида это серьёзная операция без guard-rail.

**Предложение:** confirm-modal `Утвердить N изменений?` + тост `«Снято блокировок: N»` + entry в `historyLog.js`. Если уже сделано — указать в коде комментарием что guard где-то ещё, потому что не нашли.

## 8. [LOW · FE/Perf] Перерасчёт всех 25 счётчиков на каждый рендер без мемо

**Что найдено:** на каждый ререндер (а Reactive flush триггерит renderSection при любой мутации rows) — `rows.filter(...).length` вызывается 12+ раз последовательно (`views/metrics.js:495-517`). Для 5k задач это 60k проходов. Не критично, но overkill для вкладки которая показывает 25 цифр.

**Где:** `views/metrics.js:495-517`.

**По-человечески:** вкладка лёгкая, но ленивых reduce-в-один-проход — можно. Также `assigneeLoad` пересчитывается без cache.

**Предложение:** один `rows.reduce` собирающий все 12 буккетов; либо мемоизация по `state.rows.length + last-mutation-ts`.

**Что найдено:** если на проекте 0 high и 0 medium — пользователь всё равно видит 5 пустых карточек с 0 в badges. Hero показывает «0 СИГНАЛОВ» но без позитивного фрейминга.

## Рекомендация по консолидации

Вкладка маленькая (≈100 LOC, 25 счётчиков, без drill-down). При этом конкурирует с Дашбордом (overview) и с 4 V21-дашбордами (deep-dive). Логичны 2 пути.

### Вариант A — Поглотить «Инсайты» в Дашборд (рекомендуется)

**Что делаем:** удаляем `#section-insights` из nav. Содержимое Insights переезжает в Дашборд как **отдельный room** «Сигналы» (после hero, перед charts). 3 action-кнопки сохраняем. Severity legend живёт там же.

**Pros:**
- Один экран = одна точка входа для «как дела» (overview + actionables).
- Снимает конфликт IA (КУРС — Дашборд / Метрики; Инсайты исчезает как отдельный пункт).
- В sidebar модуль КУРС схлопывается до 2 пунктов (Дашборд / Метрики) — чище.
- Дублирование с Дашбордом исчезает естественно.
- LOC -100 (убираем `InsightsView`), -1 секция HTML, -1 nav-item.

**Cons:**
- Дашборд становится длиннее (~1.5 экрана вместо 1). Митигация: collapsible room.
- Старые URL/закладки `#insights` ломаются. Митигация: redirect 301 в `app.js` router (как уже сделали для `gantt2`).

### Вариант B — Объединить «Инсайты» с 4 V21-дашбордами в один модуль СИГНАЛЫ

**Что делаем:** новый sidebar-модуль СИГНАЛЫ (заменяет лампочку «Инсайты»), внутри 5 пунктов:
1. Сводка (нынешняя `InsightsView`)
2. Точность оценок (`est-calibration`)
3. Здоровье компонентов (`component-health`)
4. Перегрузка (`burnout`)
5. Документация (`doc-debt`)

**Pros:**
- Все «найденные ИИ/алгоритмом проблемы» в одной семье.
- Даёт «Сводке» роль entry-point с deeplink-кнопками «Подробнее →» в каждый V21-дашборд.
- Mental-model очевиден: «куда смотреть когда что-то сломалось» = СИГНАЛЫ.

**Cons:**
- Нужно вытащить «Точность оценок» / «Документация» из ИНТЕГРАЦИЙ и «Перегрузку» / «Здоровье компонентов» из СОСТОЯНИЯ — много правок sidebar и ссылок.
- Зависимость от Сканнера 2.0 (V21 dashboards без него = empty state) теперь видна сразу при открытии модуля СИГНАЛЫ — но в «Сводке» она не нужна. Надо аккуратно объяснять scope.
- Имя файла `insightsDashboards.js` становится корректным, но переименовать всё равно желательно для ясности.

### Итоговая рекомендация

**Сделать вариант A**. Он закрывает 5 из 10 пунктов аудита одним движением (1, 3, 6 частично, 9, 10) и не требует крупного перетряхивания sidebar. Файл `views/insightsDashboards.js` всё равно стоит переименовать (п. 6) независимо от выбранного варианта.

Если в roadmap уже есть «семья сигналов» (СИГНАЛЫ-модуль) — тогда B, но запускать его отдельной волной после стабилизации V21 AO/AP (сейчас 4 dashboards ещё свежие, перетаскивать рано).
