# Аудит вкладки «КУРС · ДАШБОРД» — 2026-05-06 (V21)

Скоуп: `views/dashboard.js`, `index.html#section-dashboard`, `app/prizmaUI.js`, `styles.css` (`.dash-*`/`.kpi-*`/`.prizma-hero-*`).
Цель: усилить «утренний экран» тимлида Сбера. Найдено 16 пунктов в 4-х экспертных группах. Severity по шкале 🟥/🟧/🟨/⚪.

## 1. UX / Product (тимлид-утром-перспектива)

### 1.1 🟧 Hero-KPI «процент готового» вводит в заблуждение
**Где:** `views/dashboard.js:86-101` (`_renderPrizmaHeader`).
**Что:** в hero показывается `done / total * 100` по всем строкам портфеля сразу, без привязки к активному релизу/спринту. На середине квартала «57%» — это не «команда выполнила», это «исторические + закрытые из 1.20 + ещё много открытого 1.22».
**Что значит:** тимлид утром видит круглую цифру, но она ничего не значит для принятия решения «можем ли мы успеть 1.21».
**Предложение:** поменять hero-KPI на «прогресс активного релиза» (текущий спринт / окно по `RELEASE_WINDOWS` + сегодняшняя дата) с переключателем 1.20 / 1.21 / 1.22. Либо двумя числами: `28% активного релиза · 57% портфеля`.

### 1.2 🟧 Нет тренда «вчера → сегодня»
**Где:** все KPI и hero — `renderKPIs:247`, `_renderPrizmaHeader:90`.
**Что:** все цифры — снимок «сейчас». Нет дельты к предыдущему рефрешу/дню/неделе.
**Что значит:** невозможно увидеть «риски выросли на 4 за ночь» — а это и есть утренняя ценность дашборда.
**Предложение:** хранить snapshot предыдущего значения KPI в localStorage (`prizma.kpi.daily`) и показывать `Δ +3` под цифрой через `signal-drift/off-course`. На брендбуке монохром, без эмодзи.

### 1.3 🟨 Action-block ограничен 5-ю эвристиками с «магическими» порогами
**Где:** `renderActionBlock:114-228` — пороги `>5` (needs_confirm), `>30` (no_release).
**Что:** «треб. подтв. > 5» / «без релиза > 30» — захардкоженные числа. Для команды из 8 человек 30 — это весь квартал, для команды из 60 — норма.
**Предложение:** вычислить относительно `rows.length`: `needsConfirm > 0.05 * total`, `unassigned > 0.15 * total`. Вынести в `constants.js` как `ACTION_THRESHOLDS`.

### 1.4 🟨 Нет «моя команда» / personal scope
**Где:** дашборд показывает портфель целиком (`FilterEngine.getFiltered()` в `render:26`).
**Что:** тимлид часто отвечает только за 1-2 команды, остальные — шум.
**Предложение:** добавить chip-фильтр «Моя команда» поверх (использовать `state.currentUser.team` если есть, иначе persistence через localStorage). Применять до прочих расчётов в `render()`.

### 1.5 🟨 Прогресс-карточки «Всего» / «OT» — кликабельные, но «Всего» открывает modal без preset
**Где:** `renderProgress:336-379`, `onActivate:362`.
**Что:** клик по «Всего» открывает modal со всеми строками — это копия Реестра в модалке. Полезности ноль.
**Предложение:** убрать клик с «Всего» (просто agregate-индикатор) либо сделать deep-link в Реестр без модала.

## 2. Visual / Brand (соответствие BRAND_BOOK Призмы)

### 2.1 🟧 Стрелка «→» в action-footer — не из брендсета
**Где:** `views/dashboard.js:197` — `Все требующие внимания (${totalAttention}) →`.
**Что:** Юникод-стрелка `→` это типографический фолбэк. Брендбук §3.x требует SVG-иконки из набора (см. `data-icon` атрибуты в index.html — `chevron-right`/`arrow-right`).
**Предложение:** заменить на `<span data-icon="arrow-right" data-icon-size="12">` в едином стиле с топбаром.

### 2.2 🟨 Action-CTA `aria-label` дублирует видимый текст
**Где:** `views/dashboard.js:191` — `aria-label="${esc(c.cta)}: ${c.num} ${esc(c.text)}, перейти в реестр"`.
**Что:** скринридер прочтёт «Открыть: 5 задач с риском, перейти в реестр», потом ещё раз кнопку «Открыть». Это шум.
**Предложение:** оставить `aria-label` только на CTA-кнопке без дублирования (либо вообще удалить — текст в карточке уже описывает).

### 2.3 🟨 V15 Spine-pill: stripe-left есть, но не на всех «привлекающих» карточках
**Где:** `renderActionBlock:187` — `signal-${c.severity}` есть; `renderProgress:343` — нет signal-stripe; `renderKPIs:267` — `risky` получает stripe только если `>0`, остальные «secondary» без stripe.
**Что:** progress-card перегружена («OT — 35 задач при норме 30») визуально не отличается от «1.20 — 12 задач OK».
**Предложение:** прокинуть в progress-card атрибут `signal-drift` при `overload`, использовать `3px stripe-left` (CLAUDE.md § принципы дизайна).

### 2.4 🟨 H1 visually-hidden — eyebrow остаётся единственным заголовком
**Где:** `app/prizmaUI.js:58-64` (комментарий), `_renderPrizmaHeader:91`.
**Что:** `prizma-page-h1` скрыт через CSS, заголовок несёт только eyebrow «КУРС · ДАШБОРД» (caps 9-10px). Визуально страница начинается сразу с большой цифры hero — это выглядит «без шапки», но для аналитика без контекста — голо.
**Предложение:** оставить h1 видимым в одной строчке с hero-числом справа (как сейчас sub-text «Где команда сейчас находится…», но шрифт чуть крупнее), либо вернуть H1 как полу-видимый display label.

### 2.5 ⚪ Counter-badge `count-badge` в risks-summary — числа без tnum
**Где:** `renderRisksPanel:447` — `<span class="count-badge">${total}</span>`.
**Что:** CLAUDE.md требует `font-feature-settings: "tnum"` на всех числах. Если `.count-badge` не имеет tnum в styles.css — числа «прыгают» при hover.
**Предложение:** проверить styles.css на `.count-badge { font-variant-numeric: tabular-nums; }`. Если нет — добавить.

## 3. Frontend / Performance

### 3.1 🟧 Двенадцать `rows.filter(...)` в `renderKPIs` — двенадцать прохода по массиву
**Где:** `renderKPIs:247-269`.
**Что:** для портфеля 800-1200 строк делается 12 линейных проходов; в `renderActionBlock` ещё 5; в `renderProgress` (через `computeProgress`) ещё несколько; в `_renderPrizmaHeader` ещё 3. Итого 20+ прогонов.
**Что значит:** на каждом import/refresh заметная задержка, при том что один single-pass `reduce` решает всё.
**Предложение:** вычислять все агрегаты одним проходом — единый `computeDashboardCounters(rows)` в `metricsEngine.js`, возвращающий объект `{total, done, scopeYes, scopeNo, needsConfirm, r120, r121, r122, overtime, noRelease, blocking, risky, byRiskFlag, otNoPeriod, blockingNear}`. Все рендерные функции принимают этот объект.

### 3.2 🟧 `host.innerHTML = ...` ломает event-handlers, привязанные ранее
**Где:** `_renderPrizmaHeader:90-101`. На каждом `render()` блок hero+page-header перезаписывается целиком.
**Что значит:** если когда-то добавим интерактив в hero (например, переключатель релиза из 1.1) — слушатели потеряются. Также `aria-live` с `polite` срабатывает на каждый innerHTML — screen-reader будет прокрикивать «57 процентов» на каждое refresh, даже если значение не изменилось.
**Предложение:** идемпотентность — обновлять только текстовые узлы при совпадении структуры (cache hash от значений; пропускать innerHTML если ничего не поменялось).

### 3.3 🟨 `onclick`/`onkeydown` overwrite-pattern в `renderProgress` и `renderKPIs` — двойная подписка не пройдёт, но зато никакая делегация выше не работает
**Где:** `renderKPIs:299-317`, `renderProgress:369-379`.
**Что:** `el.onclick = ...` затирает свойство, что хорошо, но если родитель `section-dashboard` уже слушает делегированно — не проблема. Однако паттерн непоследовательный: `renderActionBlock:207` использует `addEventListener` (не overwrite-pattern). Между рендерами — у действий накапливаются листенеры, потому что `el.querySelectorAll('[data-filter-key]').forEach(btn => btn.addEventListener(...))` вызывается каждый раз на свежесозданных DOM-узлах (но если `innerHTML` не пересоздан — листенеры дублируются).
**Предложение:** либо все три блока на overwrite-pattern (`el.onclick =`), либо все три с делегацией от `section-dashboard`. Унифицировать.

### 3.4 🟨 Stagger через `animation-delay` ломается при быстром повторном refresh
**Где:** `_stagger:234-245`.
**Что:** при двух refresh подряд (типичный кейс импорта XLSX → notify → render → save → render) `is-emerging` ставится дважды, listener `animationend` срабатывает только один раз — второй раз класс остаётся. CSS-anim перезапускается со старта при `is-emerging` навешенном повторно — мерцание.
**Предложение:** проверить наличие `is-emerging` перед добавлением; cancel предыдущего listener; ограничить stagger только при первом mount страницы (`if (this._mounted) return;`).

### 3.5 ⚪ `setAttribute('aria-live', 'polite')` на трёх контейнерах одновременно
**Где:** `_renderPrizmaHeader:106` (heroKpi), `renderKPIs:275` (kpi-grid), и effectively на progress через innerHTML rerender.
**Что:** screen-reader получит 3 anonsements за один refresh.
**Предложение:** оставить aria-live только на одном (hero-KPI) — он несёт основное число.

## 4. Domain (квартальное планирование Сбера)

### 4.1 🟥 Релизы 1.20 / 1.21 / 1.22 жёстко зашиты — конец квартала и переход не предусмотрен
**Где:** `renderKPIs:261-263`, `renderReleaseBreakdown:458-462`, `index.html:921-924` (bulk-select).
**Что:** в коде имена `hasRelease120/121/122` и captions `1.20`/`1.21`/`1.22` хардкод. К концу квартала нужно станет `1.23/1.24/1.25` — придётся менять во всех views, а не только в одном `RELEASE_WINDOWS`.
**Что значит:** через 3 месяца дашборд лжёт — показывает «1.20» когда на дворе уже следующий квартал.
**Предложение:** ввести `state.activeReleases = [{key:'r120', label, dates, field, tf}, ...]` в `constants.js`, генерить KPI/breakdown циклом из этого источника. Уже есть частично в `RELEASE_WINDOWS` — расширить.

### 4.2 🟧 «Овертайм без периода» — детектится, но capacity-нагрузки нет
**Где:** `renderActionBlock:135-142` — `otNoPeriod`.
**Что:** мы знаем, что задача в OT без периода — но не знаем, кто её делает и есть ли у этого человека overlap с другими OT/1.22.
**Предложение:** добавить блок «Перегрузка инженеров» — кто в OT при незакрытых 1.22-задачах. Использовать `state.employees` + identity-fields из контракта 2 (CLAUDE.md). Раздельный `<details>` ниже-fold.

### 4.3 🟧 Блокирующие зависимости — порог «≤7 дней до дедлайна», но без визуализации хвоста
**Где:** `renderActionBlock:121-126`.
**Что:** мы показываем число «5 блокирующих близки к дедлайну», но не «8 — более далёкие, тоже стоит знать». Информация теряется.
**Предложение:** в action-card добавить subtitle — «5 ≤7 дн., ещё 8 в этом квартале». Один цельный signal без потери драгзвена.

### 4.4 🟨 Risk-flags drilldown свёрнут под `<details>`, но порядок флагов случайный
**Где:** `renderRisksPanel:441-451` — `Object.entries(byFlag)` без сортировки.
**Что:** в Чёрный понедельник тимлид открывает details — флаги идут в порядке вставки, не по убыванию опасности.
**Предложение:** сортировать `byFlag` по `RISK_FLAGS` order (если в `constants.js` они упорядочены по severity), либо просто `b - a` по count.

### 4.5 🟨 «Без курса / Без релиза» — единая метрика, но это два разных кейса
**Где:** `_renderPrizmaHeader:88` (`isUnassigned`), `renderKPIs:265` (`no_release`).
**Что:** «без релиза» в действительности = «бэклог + не присвоено». Бэклог — нормально, не присвоено — проблема. Сейчас всё в одной куче.
**Предложение:** ввести `isBacklog` (явное `Бэклог`) и `isUnassigned` (нет ни бэклога, ни релиза). На дашборде — `БЕЗ КУРСА = unassigned only`.

### 4.6 🟨 Нет блока «Что сделано на этой неделе»
**Где:** дашборд имеет «сделано-всего», но не «сделано за период».
**Что:** утром понедельника тимлид хочет видеть «закрыли 8 задач за неделю + закрыли 3 эпика». Это и есть positive-feedback блок.
**Предложение:** добавить блок «Прогресс за неделю» с `closedAt >= now-7d` (нужно поле `closedAt` в Row — проверить `rowFactory.js`; если нет — фолбэк по `historyLog`).
